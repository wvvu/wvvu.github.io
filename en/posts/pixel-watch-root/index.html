§0 Origins: A Cascading Ordeal Triggered by a Watch

The initial motivation was simple: I wanted to see what health metrics my Pixel Watch 2 was actually recording, and whether I could export the data myself.

The Google and Fitbit ecosystem is notoriously walled off—second-by-second heart rate has only a 2-hour retention window, ECG recordings only keep the last 5 files, and historical data can only be viewed as broad approximations inside the mobile companion app. Want direct access to raw data? There is no official API.

Rooting the watch became the sole viable path forward.

And then, everything spiraled out of control.

Root Flashing → Bootloop × 3 → Discovery of 32-bit Userspace → Root Success
→ Realizing Heart Rate Retained for only 2 Hours → Writing Archiving Daemon → Daemon Won't Wake → 6 Iterations
→ Reversing ECG Format → Bluetooth Disconnects → Forensics → Writing Utility App → Building Dashboard
→ Writing this Blog Post

A textbook case of “trying to change a lightbulb and ending up demolishing the entire house.”

§1 Three Bootloops and the Painful Lesson of “32-bit Userspace”

The Documentation Lied (Or At Least Omitted the Full Truth)

Google’s Wear OS 4 Documentation proudly featured a section titled:

64-bit kernel and user space

Seeing this, I naturally grabbed the 64-bit Magisk binary to patch init_boot.

And the watch instantly bricked. 🧱

Three Cascading Bootloops

#AttemptCause of Failure
BL1Flashing Magisk before userdata completed initial setupEncryption metadata collision
BL2Using boot_patch.sh defaulting to boot.imgPW2 uses GKI 2.0; the ramdisk resides in init_boot, while boot only contains the kernel
BL3Using 64-bit Magisk magiskinitUserspace is purely 32-bit; 64-bit ELF binaries cannot execute → init crashes

After each bootloop, I had to recover via fastboot flash init_boot init_boot.img to unbrick the device. My patience was wearing thin.

The Truth Revealed: 64-bit Kernel + 32-bit Userspace

Following the third bootloop, I calmed down and ran a full diagnostic check on the device:

$ getprop ro.product.cpu.abi
armeabi-v7a                        # ← 32-bit

$ getprop ro.product.cpu.abilist
armeabi-v7a,armeabi                # ← Not even arm64-v8a is present

$ getprop ro.product.cpu.abilist64
(empty)                            # ← 64-bit ABI list is completely empty

$ getprop ro.zygote
zygote32                           # ← Zygote is 32-bit as well

$ ls /system/lib64
ls: /system/lib64: No such file or directory   # ← Does not exist

$ zcat /proc/config.gz | grep '^CONFIG_ARM64='
CONFIG_ARM64=y                     # ← Kernel is indeed 64-bit

Conclusion: 64-bit kernel paired with a pure 32-bit userspace.

Even running Android 17, userspace remains 32-bit. This is not an oversight from launch, but a deliberate long-term architectural decision—with only 1.79 GB of RAM, 32-bit pointers yield substantial and tangible memory savings.

What the Documentation Actually Meant

Re-reading the official text closely, it didn’t technically fabricate facts:

  • The heading “64-bit kernel and user space” is a bare noun phrase that sounds like a hardware specification statement.
  • The body text is actually a call to action: “Prepare your apps for 64-bit-only hardware.”
  • The operative words were emulator (the emulator was 64-bit only) and upcoming (targeting future devices).

“Platform capability” documentation cannot be taken as ground truth for specific consumer hardware. Trust getprop, never documentation.

The Proper Procedure

The Magisk v30.7 APK packages binaries for both lib/armeabi-v7a/ and lib/arm64-v8a/. Extract the 32-bit libmagiskinit.so, patch init_boot via adb shell, and flash solely the active slot while keeping the opposite slot untouched as a backup:

# Patch on the watch (ensuring armeabi-v7a binary is utilized)
adb shell /debug_ramdisk/su -c id   # Verify root
# uid=0(root) gid=0(root) ✓

When this finally returned root, it was an immense relief.

§2 Unclickable Magisk Superuser Dialogs on a Circular Screen

The first hurdle following successful root: Magisk’s su authorization dialog had its “Grant” button cut off by the circular display boundary, rendering it impossible to click.

ADB shell running under UID 2000 was granted earlier, so adb shell su worked without issues. But any other app requesting root triggered the prompt—with the confirmation button positioned entirely in the clipped outer corner of the circular panel.

Inspecting magisk.db directly:

-- settings table:
('bootloop', 0)        -- su_auto_response was completely absent!

-- policies table:
(2000, 2, 0, 1, 0)     -- Only the shell UID was granted

My previous attempt executing REPLACE INTO settings ... su_auto_response=2 never committed to the database—quotes were stripped clean during the three-stage relay across bash → adb shell → su -c.

Surgical Solution: Inject the target application’s UID directly into the policies table:

# Query UID
adb shell dumpsys package <package_name> | grep -m1 userId=

# Grant permission (policy=2 = ALLOW, until=0 = permanent)
adb shell /debug_ramdisk/su -c "magisk --sqlite \
  \"INSERT OR REPLACE INTO policies (uid, policy, until, logging, notification) \
    VALUES (<uid>, 2, 0, 1, 0)\""

Magisk queries the table dynamically on each su request, taking effect immediately without restarting the daemon.

Pitfall: In magisk --sqlite "SELECT * FROM settings", the * wildcard gets expanded by the shell glob into /data/adb/adb_keys. The most reliable approach is pulling magisk.db to inspect and edit locally.

This was the revelation that caused real concern:

2 hours! Raw, second-by-second heart rate records remain on the watch for merely 120 minutes.

Moreover, the cleanup routine is embedded directly in the write path—it is not executed by a scheduled timer, but triggered whenever new data arrives that is more than 5 minutes newer than the previous cleanup pass. Completely irrespective of whether data was synced to the cloud, un-archived offline data older than 2 hours is permanently erased at the source.

The only safeguard for CleanWorker is requiresCharging = true—the 30-day cleanup only triggers while the device is on a charger. However, the 2-hour heart rate cleanup is entirely unconstrained by charging status.

This implies: Without external intervention, out of 24 hours of daily heart rate recordings, you can inspect at most the trailing 2 hours on the watch.

I immediately began building an archival system.

§4 Second-by-Second Heart Rate Lifeline: Six Generations of Daemon Evolution from v1 to v6

Architecture

On-Watch Daemon (60-minute polling)
  ├─ Copies 13 Fitbit databases + ECG → /data/local/tmp/hr_archive/snap/
  ├─ mtime deduplication (skips unmodified files)
  ├─ Skips non-empty journal files (prevents torn database snapshots)
  └─ Rolling retention window (default 730 days)

PC Script (archive_hr.py)
  ├─ Incremental ADB pull from snap/
  ├─ Smart SQLite merge into hr_archive.db
  └─ Raw ECG payload preservation

On paper, this seemed straightforward. In practice, it sparked a three-day debugging ordeal around daemon scheduling.

v1–v2: The Naive sleep 3600

# Initial implementation
while true; do
    archive_once
    sleep 3600   # Archive once every hour
done

Failure: Over the first 22 hours after deployment, it executed only once upon system boot.

Forensic logs showed that the sleep 3600 child process entered sleep at 10:41 and did not wake until 13:44—nearly 3 hours later.

Root Cause: sleep in toybox relies on CLOCK_MONOTONIC, which excludes system suspend time. Smartwatches spend the overwhelming majority of time in deep suspend, during which the monotonic clock pauses. To accumulate one hour of awake time, the watch required hours of real time.

Hard-Learned Lesson: A living process ≠ a running service. Monitor concrete outputs and log intervals.

I permanently lost second-by-second heart rate data spanning 09-18 12:44 to 09-19 11:32, including an entire night of sleep metrics.

v3: Small Sleep Slices + Wall Clock

# v3 modification
chunk=30   # 30-second sleep slices
next_at=$(( $(date +%s) + interval ))
while [ "$(date +%s)" -lt "$next_at" ]; do
    sleep "$chunk"
done
archive_once

Outcome: Daytime operation normalized, with 2-minute test cycles exhibiting errors <1 minute. Reverted to a 60-minute production cycle.

v4: 30 Seconds Failed Overnight

Failure: From 03:03 to 08:17 on 09-20, the daemon remained asleep for 5 hours and 14 minutes.

A 30-second monotonic slice still failed to accumulate during deep overnight sleep. Reduced chunk size to 5 seconds.

v5: 5 Seconds Still Failed Deep Suspend

Failure: Early morning 03:52 to 06:36 slept for 2h44m; 06:36 to 09:39 slept for 3h03m.

Root Cause: The system enters deep suspend at night, freezing monotonic time completely. Sleep slicing only helps verify elapsed time once the system is awake; it cannot force the system to wake when an alarm matures.

v5 Exploration: Kernel RTC Hardware Alarm

Introduced kernel-level RTC alarms:

echo "$next_at" > /sys/class/rtc/rtc0/wakealarm

When the target epoch is reached, the PMIC forcibly wakes the Application Processor (AP), regardless of sleep depth.

A new obstacle arose: When wakealarm rouses the AP, absent an active wakelock, the system remains awake for approximately 400 milliseconds before returning to suspend. With chunk=5s, monotonic sleep could only accumulate 0.4s within that window. The sleep call failed to return before the hardware alarm expired—stalling the daemon again.

v6: The Ultimate Solution

chunk=0.3   # 300ms < 400ms wake window

Core Principle: The sleep slice must be shorter than the RTC wake window (~400ms), ensuring that within the hardware wake window, sleep is guaranteed to return, evaluating now_epoch >= next_at and triggering archival.

Accompanying enhancements:

  • Prior to archival, acquire a wakelock via cmd power set-wakelock acquire PARTIAL_WAKE_LOCK to prevent suspend during disk operations.
  • Release wakelock once archival finishes.
  • Check daemon PID validation every 10 cycles (~3 seconds) to minimize high-frequency storage I/O.
  • Stop commands execute kill -9 on the daemon, toybox pkill -9 -P on child processes, and reset wakealarm.

Final State: Minute-accurate 60-minute polling cycles, strictly respecting the 2-hour retention deadline even across deep overnight suspend.

§5 ECG Decoding: Reversing libecg.so to Crack the BIFA Format

Format Overview

Raw ECG recordings are stored at /data/data/com.fitbit.ecg/ecg-*.dat, each file possessing a fixed length of 19,858 bytes.

Through static reverse engineering of libecg.so (ECGlib) extracted from the com.fitbit.ecg APK, paired with dual-sample statistical cross-validation, the complete binary specification was determined:

[0,4)     magic "BIFA" ("AFIB" spelled backwards—atrial fibrillation detection)
[4,8)     u32 little-endian, data payload length
Data Area:
  0x00    12B    Static segment (version / flags)
  0x0D    f32    ~94.05 / 98.59 (suspected heart rate)
  0xDD    u32    Sample count = 7500
  0xE1    15000B ★ ECG Waveform: 7500 int16 little-endian samples @ 250Hz = 30.0 seconds
  Frame Timestamp Table: 469 × 8B (u32 microseconds, u32 0)
  Annotations:
    469B  Frame validity flags
    3×f32 Signal quality (valid / artifact / noise)
    u16[] QRS onset sequence (trigger points for cardiac cycles)
  Trailing 32B Checksum (keyed algorithm, unresolved)

Decoder Implementation

MAGIC = b'BIFA'
FS_HZ = 250.0  # Fitbit ECG sampling frequency

# Read raw waveform
n_samples = struct.unpack_from('<I', body, 0xDD)[0]  # = 7500
wave_raw = body[0xE1:0xE1 + n_samples * 2]
samples = np.frombuffer(wave_raw, dtype='<i2').astype(np.float32)
# → 7500 sample points, 30.0s @ 250Hz raw ECG waveform

The R-Peak Detection Pitfall

The first iteration used argmax(|s|) to locate the R-peak, which was thrown off by a -32768 saturation value at second 29.776 in ecg-001 (caused by lost contact). While it had the maximum absolute amplitude, it was an artifact rather than an R-wave.

Resolution: Mask saturation artifacts (|s| > 30000) → remove baseline drift → detect maximum positive deflection:

def first_rpeak(s):
    sat = np.abs(s) > 30000          # Saturation artifact
    x = s.copy()
    x[sat] = np.nan
    base = float(np.nanmedian(x))    # Baseline subtraction
    x = x - base
    x[sat] = -np.inf                 # Exclude candidates
    return int(np.argmax(x))         # Authentic R-peak

Unresolved Elements

  • Checksum algorithm (trailing 32 bytes with first 16 bytes active; keyed algorithm, not raw MD5/SHA1/SHA256/CRC64).
  • Semantic meaning of 0x00065B8F in the trailing 16B annotation region.
  • Full semantics of metadata fields between 0x00 and 0xDC.
  • rsp-*.dat server responses encrypted with A128GCM; lacking keys, left untouched.

§6 Bluetooth Disconnection Forensics: The Mystery of the 157-Second Silence

The Bluetooth link between phone and watch frequently disconnected. Phone logs initially suggested the watch was “failing to respond to paging requests.” I validated this from the watch perspective.

00:25:49.515  -running                                   ← Returns to suspend
      ┌────────────────────────────────────────┐

      └────────────────────────────────────────┘

00:28:26.511  ACL Connection request                     ← Reconnection completes within 145ms

Consistent across 4 out of 4 cases: Lost link duration strictly equaled AP suspend duration.

Root Cause Analysis

Capabilities reported by the watch’s Qualcomm WCN Bluetooth controller:

sniff_offload_support: 0           ← Link power-saving cannot be offloaded to controller
le_connectability_state: "DISARMED" ← Autonomous incoming connection offload is disarmed

The controller lacks autonomous connection acceptance offload while the AP is suspended. Once the AP enters sleep, inbound connections cannot complete—authentication, encryption, SDP, and RFCOMM link establishment require host interaction.

An Analytical Trap

“Absence of a Connection request on the host” does not prove “the radio never received paging signals.”

BR/EDR page responses (FHS packets) are resolved at the controller layer. If the controller returns FHS but the phone fails to receive it, the connection stalls before alerting the host stack. HCI-level logs are required to distinguish this edge case.

§7 COMPANION_PROXY: A Transparent TCP Proxy Disguised as a Network

While investigating how the watch accesses the internet, I uncovered an elegant architectural component.

Initial Misconception

“The Companion Proxy (COMPANION_PROXY)? Just a phone tunneling utility, unrelated to standard IP traffic.”

Incorrect. It is the core connectivity mechanism.

Empirical Observations

Upon disabling Wi-Fi, the watch registered the following network interface:

NetworkAgentInfo{
  network{112}
  ni{COMPANION_PROXY CONNECTED}
  nc{ Transports: BLUETOOTH
      Capabilities: INTERNET & VALIDATED & NOT_METERED & NOT_VPN }
  lp{ InterfaceName: lo
      Routes: [0.0.0.0/0 -> 127.0.0.1 lo] }
}
Active default network: 112   ← Selected as the default network route

What Is It Really?

Neither a Wi-Fi hotspot nor Bluetooth PAN, but a transparent application-layer TCP proxy masquerading as a network.

Composed of three pillars:

  1. A root process listening on a loopback socket:

    tcp 0 0 127.0.0.1:59523 0.0.0.0:* LISTEN  /sysproxy

  2. An iptables rule redirecting outbound TCP traffic to that port:

    iptables -t nat → REDIRECT tcp 0.0.0.0/0 → redir ports 59523

  3. The loopback interface configured as the default gateway: Routes: [0.0.0.0/0 -> 127.0.0.1 lo]

Complete Network Path:

App issues TCP connection → Kernel routes to lo → iptables REDIRECTs to 127.0.0.1:59523
→ /sysproxy handles socket → Relays over Bluetooth Data Layer tunnel to phone
→ Phone performs outbound connection on behalf of watch → Returns via same path

Structural Comparison

DimensionWi-Fi Hotspot / BT PANCOMPANION_PROXY
OSI LayerNetwork Layer (True IP Interface)Application Layer (Transparent TCP Proxy)
Interfacewlan0 / bt-panlo (Loopback)
Egress HostWatch directlyPhone on watch’s behalf
Independent IPYesNo

Practical Consequence: Keeping your phone nearby with Bluetooth active provides full-day internet access for the watch without consuming Wi-Fi, eSIM profiles, or cellular plans.

A Setup Pitfall

I had previously configured a persistent proxy via http_proxy=192.168.1.9:10808 pointing to my desktop workstation. While fine at home, leaving the house rendered 192.168.1.9 unreachable → proxy-aware traffic stalled on connection timeouts → congesting COMPANION_PROXY → manifesting as broken Bluetooth syncing.

Because COMPANION_PROXY natively tunnels standard TCP traffic, setting an auxiliary HTTP proxy on the watch is both redundant and problematic.

§8 On-Watch Toolbox: QuickTools App and Module-Free SSH

PW2 QuickTools

To simplify toggling proxy settings, SSH, Wi-Fi, and ADB, I developed QuickTools—a lightweight dashboard tailored for the circular Wear OS display:

  • SSH Toggle: Starts or terminates sshd
  • Wi-Fi Toggle: Overrides Wear OS Clockwork policy engine suppression
  • Proxy Editing: Input fields limited to the trailing two octets 192.168.__.__, avoiding typing long strings on a small screen
  • Proxy Toggle: One-click enable/disable of system HTTP proxy
  • ADB Toggle
  • Connectivity Probe: Probing Google 204 endpoints

Handling Wi-Fi Policy Suppression

Wear OS utilizes a Clockwork policy engine—invoking cmd wifi set-wifi-enabled enabled alone is suppressed into sleep state by the OS whenever Bluetooth is connected. All three properties must be set together:

settings put system clockwork_wifi_setting on
settings put global wifi_always_requested 1
cmd wifi set-wifi-enabled enabled

Why Connectivity Probing Cannot Rely on ICMP Ping

Reasons:

  1. COMPANION_PROXY is a TCP proxy whose iptables rules match exclusively TCP; ICMP packets bypass sysproxy and get dropped.
  2. Android applications lack CAP_NET_RAW; InetAddress.isReachable() falls back to TCP port 7 echo checks, yielding false negatives.
  3. Ping replies confirm packet delivery, but do not confirm DNS resolution or proxy traversal.

Robust Approach: Perform an HTTP GET to https://www.gstatic.com/generate_204, expecting an HTTP 204 response. Zero-byte response payload minimizes data and power consumption.

Standalone, Module-Free OpenSSH

Avoid installing Magisk modules—modules run scripts under /data/adb/modules/<id>/ during early boot as root. Script errors easily cause unrecoverable bootloops.

The safer approach: push a 32-bit OpenSSH binary bundle directly to /data/local/tmp/ssh/ and launch manually:

LD_LIBRARY_PATH=/data/local/tmp/ssh/lib \
  /data/local/tmp/ssh/bin/sshd -f /data/local/tmp/ssh/etc/sshd_config -p 2222

Key configuration nuance: Android lacks /etc/passwd. The following must be present in sshd_config:

UsePrivilegeSeparation no
StrictModes no

Orphaning the process to init (PPID=1) ensures the server remains listening on 0.0.0.0:2222 regardless of screen timeout or closing the management app. Consumes 0% power when idle, with zero bootloop risk.

Connect directly from the workstation:

ssh pw2        # Directly connects to 192.168.1.10:2222 as root with key authentication

§10 Miscellaneous Pitfalls and Red-Line Checklist

Critical Precautions

  • ❌ Never click “Direct Install / Fix Environment” inside Magisk.
  • ❌ Do not flash boot.img; flash exclusively init_boot.
  • ❌ Avoid applying standard system OTAs (A/B partition writes wipe root modifications).
  • ❌ Do not install Magisk modules.
  • ❌ Preserve the pristine init_boot.img backup (essential for unbricking).

Intercepting OTAs

When quarterly OTAs are distributed, connecting the device to a charger causes update_engine to write official system images to the inactive slot in the background, invalidating root upon reboot.

# Terminate and reset update_engine
update_engine_client --cancel
update_engine_client --reset_status
setprop ctl.stop update_engine

# Wipe downloaded OTA staging cache
rm -rf /data/ota_package/*

# Disable GMS update services
pm disable com.google.android.gms/.update.SystemUpdateService
pm disable com.google.android.gms/.update.SystemUpdateWearableActivity
pm disable com.google.android.gms/.update.SystemUpdatePersistentListenerService
pm disable com.google.android.gms/.update.SystemUpdateGcmTaskService

Suppressing Play Store Background Wakelocks

Google Play Store wakes frequently while charging (holding wakelocks for up to 2 minutes 40 seconds, leading to heat buildup):

pm disable com.android.vending/com.google.android.finsky.scheduler.process.mainimpl.PhoneskyJobServiceMain
pm disable com.android.vending/com.google.android.finsky.scheduler.process.backgroundimpl.PhoneskyJobServiceBackground

Manual updates through the Play Store interface remain fully functional.

Permanent ADB Authorization Across Reboots

adb push ~/.android/adbkey.pub /data/local/tmp/
adb shell su -c "cat /data/local/tmp/adbkey.pub >> /data/misc/adb/adb_keys"
adb shell su -c "chown system:shell /data/misc/adb/adb_keys"
adb shell su -c "chmod 640 /data/misc/adb/adb_keys"
adb shell su -c "restorecon /data/misc/adb/adb_keys"

Plug-and-play authorization persists permanently across system reboots.

Lessons Learned

  1. Trust getprop, not documentation. Three bootloops stemmed entirely from trusting documentation instead of inspecting hardware properties.
  2. A running process ≠ an active service. Always evaluate output logs. A frozen sleep process cost an entire night of heart rate records.
  3. Embedded systems operate multiple clocks. The fact that CLOCK_MONOTONIC halts during suspend is rare on servers, but a critical concern on low-power embedded devices.
  4. Decompilation beats official claims. Fitbit’s 2-hour retention limit, CleanWorker charging requirements, and the ECG BIFA format are completely undocumented.
  5. COMPANION_PROXY is remarkably elegant. No hotspots, no PAN—a simple loopback routing paired with an iptables redirect and Bluetooth data tunnel provides transparent TCP connectivity.

Experience with AI Assistance

AI accelerated many facets of the project:

  • Reverse engineering ECG payloads and generating Python decoders
  • Iterating multiple revisions of the background daemon
  • Drafting forensic analysis summaries
  • Frontend visualization design
  • Formatting structured Markdown reports

However, AI also introduced notable bugs—such as treating saturation values as R-peaks, falling into substring traps with grep -q running, and overlooking monotonic sleep during system suspend. Each error was caught through testing on physical hardware.

AI is an exceptional accelerator, but never the final arbiter. Verification on real devices remains the ultimate standard of truth.

Closing Thoughts

This small smartwatch, constrained to 1.79 GB of RAM, proved far more intricate than initially anticipated. From 32-bit userspace to RTC hardware alarms, and from iptables redirects to Bluetooth controller offloading limits—every layer held its own story.

The journey was full of setbacks, but thoroughly rewarding.

And best of all—I can finally view and own my entire health dataset. That alone made it worthwhile.
