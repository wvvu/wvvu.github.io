Modern Browser Data Sovereignty Dilemma and Defense Breakthrough: Reverse Engineering and Cross-Machine Migration of Chrome App-Bound Encryption (ABE)

2026-10-09 14:28 UTC

Testbed: Windows 11 x64 / Google Chrome 154.0.8037.99 ➔ 155.0.8059.40
Core Topics: Windows DPAPI, App-Bound Encryption (ABE), COM Privilege Elevation Interface, Host Sovereignty, Cross-Machine Cookie Migration

Abstract

In traditional endpoint security models, “the owner of the physical machine and operating system is the ultimate sovereign of the system” is a foundational axiom. However, with the evolution of modern browser sandboxing and credential protection mechanisms, application software has begun attempting to defend against “non-privileged and even privileged processes running on the very same host.” App-Bound Encryption (ABE), introduced by Google Chrome starting with version 127, is a prime exemplar of this defensive philosophy.

This article documents a complete reverse engineering analysis, live penetration test, and cold migration practice targeting the ABE architecture in Chrome versions 154 through 155. We systematically deconstruct ABE’s “four-layer matryoshka encryption scheme” (SYSTEM DPAPI ➔ USER DPAPI ➔ Path Whitelist ➔ Binary Internal Obfuscated Encryption), analyze why simple file-level cold copying inevitably fails both mathematically and architecturally, and achieve lossless extraction of the master encryption key by invoking the COM elevation interface through a crafted legitimate path. Finally, we evaluate a session re-injection strategy powered by the Chrome DevTools Protocol (CDP) and reflect on browser data ownership versus Mozilla Firefox’s portable design philosophy from an architectural perspective.

1. Background and Threat Model Evolution

1.1 The Classical DPAPI Era and the Rampancy of Infostealers

Prior to Chrome 127, Chromium’s credential protection on Windows relied on native Windows DPAPI (CryptProtectData):

  • The master key (a 32-byte AES key) was encrypted via user-level DPAPI and stored in Base64 encoding inside os_crypt.encrypted_key within Local State (prefixed with DPAPI);
  • Sensitive database fields within Cookies and Login Data were encrypted via AES-256-GCM, with ciphertext prefixed by v10.

Because Windows DPAPI was designed under the premise of “protecting data from being accessed by other Windows accounts,” any process executing under the current user’s security context (Medium Integrity Level) could transparently decrypt the key simply by calling CryptUnprotectData. This design led to the unchecked proliferation of information-stealing malware (infostealers) such as RedLine, Lumma, and Vidar—adversaries required no administrative privileges whatsoever to harvest a user’s entire collection of cookies and saved credentials in bulk.

1.2 Google’s Defensive Hypothesis: Defending Against Burglars or Landlords?

To disrupt the economics of infostealer malware, Google rolled out App-Bound Encryption (ABE) starting in Chrome 127. Its core design objective is:

“Even if an adversary acquires code execution privileges under the current user, they cannot decrypt browser credentials unless they are executing within a legitimate chrome.exe process.”

To enforce this, Chrome introduced a highly privileged background daemon operating under NT AUTHORITY\SYSTEM—elevation_service.exe. Consequently, control over credentials was moved away from the standard “user data directory” into a multi-layered defensive mesh woven from kernel-level privileges, COM interfaces, and proprietary internal binary algorithms.

2. Chrome ABE’s Four-Layer Matryoshka Protection Mesh

Through reverse engineering of the Chrome 154/155 binaries and Chromium source code (elevator.cc, caller_validation.cc), the encapsulation format of the ABE master key can be fully reconstructed as follows:

Local State · os_crypt.app_bound_encrypted_key (Base64)
  │
  └─ [4-byte magic: "APPB"]
       │
       └─ [Layer 1: SYSTEM DPAPI Envelope] (640 bytes)
            │
            └─ [Layer 2: USER DPAPI Envelope] (384 bytes, szDataDescr="Google Chrome")
                 │
                 └─ [Layer 3: Path Validation Header] (35 bytes)
                 │    ├─ [4B len=31]
                 │    ├─ [1B level=0x02 (PROTECTION_PATH_VALIDATION)]
                 │    └─ [30B "C:\Program Files\Google\Chrome"]
                 │
                 └─ [Layer 4: Internal Ciphertext Payload] (93 bytes)
                      ├─ [1B ver=0x03]
                      ├─ [32B KSP Ciphertext]
                      ├─ [12B GCM Nonce]
                      ├─ [32B GCM Ciphertext] (The authentic 32-byte AES Master Key)
                      └─ [16B GCM Tag]

2.1 First Lock: NT AUTHORITY\SYSTEM DPAPI

Once the APPB magic header is stripped, the outermost layer is encapsulated by elevation_service.exe in the SYSTEM context via DPAPI.

  • Target Threat: Low-to-medium privilege malware running under normal user privileges.
  • Interception Behavior: When an unprivileged process invokes CryptUnprotectData, the underlying system directly returns 0x8009000B (NTE_BAD_KEY_STATE), because the cryptographic blob belongs to the pseudo-account S-1-5-18.

2.2 Second Lock: Current User DPAPI

Once the outer layer is stripped, the exposed 384-byte payload remains a complete DPAPI blob, whose descriptor is the UTF-16 encoded string Google Chrome.

  • Target Threat: Independent malicious background services running in Session 0 or lateral-moving SYSTEM processes.
  • Mechanism: Even if an adversary gains SYSTEM privileges, without loading or impersonating the currently logged-in user’s credentials (lacking the user’s DPAPI MasterKey), they cannot decrypt this layer. Only via token impersonation—borrowing the user token of explorer.exe—can both barriers be crossed simultaneously.

2.3 Third Lock: Caller Path Validation (caller_validation)

Decoupling the second layer does not yield the raw symmetric key, but rather a structured packet prefixed with length headers: [len=31][level=0x02]["C:\Program Files\Google\Chrome"][payload_len=93][payload].

  • In the COM implementation of elevation_service.exe, the service inspects the executable path of the calling process via QueryFullProcessImageNameW;
  • Only when the caller strictly matches C:\Program Files\Google\Chrome after directory normalization does the service proceed to the subsequent stage.

2.4 Fourth Lock: Proprietary Internal Algorithm (PostProcessData)

Under official release build flags (GOOGLE_CHROME_BRANDING), the 93-byte payload is processed through proprietary obfuscated cryptographic logic: $$\text{AES_Key} = \text{NCryptDecrypt}(\text{payload}[1:33]) \oplus \text{Hardcoded_XOR_Key}$$ $$\text{Master_Key} = \text{AES-256-GCM}_{\text{AES_Key}}(\text{payload}[45:77])$$

Inside the compiled binary, this XOR key is stored statically at a specific offset and bound to Windows CNG (Cryptography Next Generation) persistent keys. Offline calculation outside the service context consistently fails due to missing CNG keys.

3. Why Physical File Overwriting Inevitably Fails

When migrating machines or restoring backups, users frequently copy the entire %LOCALAPPDATA%\Google\Chrome\User Data directory. Under ABE, this triggers an irrecoverable chain reaction:

[Target machine launches Chrome]
       ↓
1. Reads app_bound_encrypted_key from Local State
       ↓
2. Cross-calls elevation_service.exe locally on target machine
       ↓ [Point A: DPAPI machine key mismatch]
       ↓ Target machine lacks source machine's LSA private key; CryptUnprotectData yields 0x80090005
3. Chrome determines master key is corrupted, triggering fallback degradation:
   [Instantly generates a brand new 32-byte random key on the target machine and writes to Local State]
       ↓
4. Chrome loads migrated SQLite database (Network\Cookies)
       ↓ [Point B: AES-GCM tag verification failure]
       ↓ Uses new key to decrypt legacy v20 fields; Authentication Tag validation fails across all records
5. Chrome assumes database has been tampered with or corrupted:
   [Executes silent purge, wiping the entire database clean]

While this mechanism guarantees that “stolen databases cannot be decrypted offline by third parties,” it simultaneously obliterates legitimate data backup and migration workflows for device owners.

4. Hands-on Reversing: Path Trimming Flaw and COM Interface Penetration

In adversarial security research, boundary conditions in validation logic often serve as the key to breaking through defensive barriers.

4.1 Discovering the Edge Flaw in MaybeTrimProcessPath()

Examining caller_validation.cc within the Chromium source tree reveals the path normalization routine:

  1. Retrieve the absolute path of the calling process;
  2. Strip the trailing .exe extension;
  3. If the parent directory name happens to be Application, Temp, or a version string directory, strip one additional directory component;
  4. Perform an exact size == size && std::equal comparison between the trimmed path and the expected string.

This implies:

  • A standard Chrome installation sits at C:\Program Files\Google\Chrome\Application\chrome.exe. Stripping two layers yields C:\Program Files\Google\Chrome;
  • If an arbitrary executable is placed directly under the root directory C:\Program Files\Google\Chrome\ (e.g., C:\Program Files\Google\Chrome\launcher.exe), stripping .exe yields the exact same string: C:\Program Files\Google\Chrome.

4.2 Bypassing Process Injection: Native Proxy Invocation

Traditional penetration testing utilities typically inject a DLL into a running chrome.exe instance, which easily alerts EDR and endpoint antivirus engines. The aforementioned path flaw provides a clean bypass without requiring process injection:

  1. Acquire Administrator privileges (UAC elevation);
  2. Temporarily drop a binary into C:\Program Files\Google\Chrome\;
  3. Initialize COM inside the binary and establish a connection to the elevated interface:
    • CLSID: {708860E0-F641-4611-8895-7D867DD3675B}
    • IID: {1BF5208B-295F-4992-B5F4-3A9BB6494838} (IElevator2Chrome)
  4. Configure PKT_PRIVACY and dynamic cloaking (DYNAMIC_CLOAKING) via CoSetProxyBlanket;
  5. Invoke the DecryptData method (index 5 in the virtual function table).

Because the caller’s physical path satisfies the whitelist condition, elevation_service.exe automatically completes SYSTEM DPAPI decryption, user token impersonation decryption, and internal PostProcessData routines within its own privileged process, returning the final 32-byte plaintext master key directly to the caller.

5. Version Leap Verification: Chrome 154 ➔ 155 Coupling Analysis

To evaluate the robustness and lifespan of this exploitation chain, we performed validation across a major version upgrade.

5.1 Verification Hypotheses

  • Backward Compatibility: During updates, Chrome cannot discard or rotate existing master keys; doing so would invalidate active user sessions en masse.
  • Defensive Patching: Has Google amended the path trimming routine in version 155 (such as introducing Authenticode digital signature checks)?

6. Cross-Machine Migration: Physical Reversing Blindspots and CDP Runtime Breakthrough

Having acquired the host machine’s 32-byte master key, we advanced the experiment toward its ultimate goal: losslessly migrating active sessions into an isolated virtual machine (VM).

6.1 The Waterloo of Physical Re-encryption

We initially designed an offline physical re-encryption approach:

Utilize IElevator::EncryptData (vtable index 4) locally inside the VM to re-encrypt the 32-byte master key into an app_bound_encrypted_key native to the VM’s hardware profile, then overwrite the database files directly.

However, upon launching Chrome inside the VM, the database was wiped entirely within milliseconds.

Why Did Calling Official EncryptData Still Fail?

Binary analysis of databases extracted from the VM revealed the most insidious safeguard in the ABE architecture:

  • When an external utility invokes EncryptData, elevation_service generates an identity token via GenerateValidationData. This token not only checks the directory, but also imprints the specific binary identity of the creator;
  • When the authentic chrome.exe launches and attempts to read the key, validation detects that “creator and consumer are distinct entities,” throwing kErrorInvalidValidationData;
  • Conclusion: Any attempt to manufacture an encrypted wrapper for Chrome outside its legitimate process boundary is blocked by its closed-loop validation.
   [External Tool] ── EncryptData ──> Produces ciphertext with external signature token
                                           │
   [chrome.exe Reads] ── DecryptData ──> Signature validation fails (kErrorInvalidValidationData)
                                           │
                                           └──> Triggers circuit breaker: Resets master key and purges database

6.2 The Elegant Solution: CDP Runtime Network Injection

With cold writes blocked, the optimal path shifted to runtime injection: letting the legitimate chrome.exe within the VM write credentials to disk itself in a trusted context.

Utilizing Chrome’s native Chrome DevTools Protocol (CDP), the entire migration pipeline was restructured:

[Host System]
  │  1. Decrypt host Cookies.db offline (using extracted 32B master key)
  │  2. Strip 32B domain-binding hash prefix (sha256(host_key))
  │  3. Reconstruct into structured CDP-compliant objects (URL / Domain / Path / SameSite / Secure)
  │
  └──[ SSH Port Forwarding Tunnel (Port 9223 ➔ VM 9222) ]
        │
[Virtual Machine]
  │  4. Launch official VM chrome.exe (--headless=new --remote-debugging-port=9222)
  │  5. Host script attaches to Page Target WebSocket
  │  6. Batch invoke Network.setCookies to inject session state
  │  7. Send Browser.close graceful shutdown signal
  │  8. Native VM watchdog invokes trusted APIs, re-encrypting all cookies with native ABE keys to disk

Key Implementation Pitfalls and Mitigations:

  1. Strict URL Mapping: Passing solely the domain field causes CDP to silently drop cookies bearing security attributes due to missing origin context. URLs must be synthesized strictly as https://[domain][path] according to is_secure.
  2. SameSite Constraints: Modern Chromium mandates that cookies with SameSite=None must have secure=True, otherwise the underlying CookieMonster component rejects them outright.
  3. Validation: Through this method, across 3,635 active cookies on the host, excluding 454 naturally expired sessions, all remaining 3,181 active cookies were injected and persisted into the VM’s storage with a 100% success rate. Launching Chrome inside the VM retained full logged-in sessions for NetEase Cloud Music, Google, TikTok, and other platforms without interruption.

7. Reflections and Insights: The Watershed of Data Sovereignty and Architecture Philosophy

7.1 Server-Side Perspective: The Schrödinger State of Dual-Device Token Equivalence

Throughout this experiment, the host and VM concurrently held identical JWTs and session cookies. Yet, major platforms raised no anomaly flags. The reasons:

  • Mathematical Nature of Stateless JWTs: Modern identity verification relies on asymmetric digital signatures. As long as signatures validate and tokens are unexpired, servers typically do not enforce real-time hardware binding;
  • Natural Masking via NAT Topology: Bridged via host NAT, the VM shares an identical public IP. Coupled with matching OS and browser builds, canvas, WebGL, and TLS fingerprints overlapped substantially, appearing to risk engines as routine multi-tab browsing.

7.2 Client-Side Perspective: Architectural Divergence Between Chrome and Firefox

This multi-hour exploration across privilege escalation, reverse engineering, COM interface penetration, and network injection ultimately leads to an architectural reflection:

+-----------------------------------+-----------------------------------+
|        Google Chrome (ABE)        |          Mozilla Firefox          |
+-----------------------------------+-----------------------------------+
| · Hardware/system tied (DPAPI/LSA)| · Open portable standard (pure FS)|
| · Assumes host untrusted (vs user)| · Assumes owner has sovereignty   |
| · Strips migration for paper-def  | · Free profile folder migration   |
| · Device upgrade friction: High   | · Device upgrade friction: Low    |
+-----------------------------------+-----------------------------------+

Chrome’s ABE illustrates engineering defense at its extreme complexity, but it falls into a classic Von Neumann architectural paradox:

“On a host system where a user possesses local physical and administrative sovereignty, attempting to use user-space logic and routine system services to completely strip that owner’s access to their own data is fundamentally an endless cat-and-mouse game.”

Google layered SYSTEM DPAPI, user DPAPI, path verification, and binary obfuscation, yet none of it could stop properly positioned native code. The real cost of this arms race is borne by millions of legitimate users who struggle to migrate their data across devices and lose autonomy over their own digital footprint.

8. Conclusion and Responsible Disclosure

The technical explorations documented herein were conducted in isolated, fully controlled, and lawful experimental environments (local host and virtual machines). All real cryptographic master key fingerprints, private session tokens, and sensitive network topology details have been scrubbed. This document aims to offer first-hand engineering evidence for endpoint security designers evaluating system security, cryptographic practices, and anti-infostealer defensive architectures.

In an era of increasingly privatized digital assets, security evolution is welcome, but future system design must rediscover a balanced harmony between “security boundaries” and “user data sovereignty.”
