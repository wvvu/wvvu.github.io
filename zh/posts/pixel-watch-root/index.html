§0 起因：一块表引发的连锁折腾

事情的起因很简单：想看看自己的 Pixel Watch 2 到底在记录哪些健康数据，能不能自己导出来。

Google 和 Fitbit 的生态非常封闭——心率数据只有 2 小时窗口，ECG 心电图只留最近 5 条，历史数据只能在手机 App 里看个大概。想拿到原始数据？对不起，没有官方接口。

于是，Root 这条路就成了唯一选择。

然后，一切就失控了。

刷 Root → Bootloop × 3 → 发现 32 位用户空间 → 成功 Root
→ 发现心率只留 2 小时 → 写归档守护 → 守护不醒 → 6 版迭代
→ 逆向 ECG 格式 → 蓝牙断连 → 取证 → 写工具 App → 做可视化面板
→ 写这篇 blog

典型的「修一个灯泡，最后把整栋房子拆了」。

§1 三次 Bootloop 与「32 位用户空间」的血泪教训

文档说谎了（或者说，没有说全部的真话）

Google 的 Wear OS 4 文档 有一节标题赫然写着：

64-bit kernel and user space

中文版翻译：「64 位内核和用户空间」。

看到这个，那理所当然地下载了 64 位的 Magisk 二进制来 patch init_boot。

然后表就变砖了。 🧱

三次连环 Bootloop

#尝试死因
BL1在 userdata 初始化完成前就刷 Magisk加密元数据冲突
BL2用 boot_patch.sh 默认打 boot.imgPW2 是 GKI 2.0，ramdisk 在 init_boot 分区，boot 里只有 kernel
BL3用 64 位 Magisk magiskinit用户空间是 32 位，64 位 ELF 无法执行 → init 崩溃

每次 Bootloop 后都得 fastboot flash init_boot init_boot.img 把原版刷回去救砖。心态逐渐崩溃。

真相大白：64 位内核 + 32 位用户空间

终于在第三次之后冷静下来，上设备跑了一圈自查：

$ getprop ro.product.cpu.abi
armeabi-v7a                        # ← 32 位

$ getprop ro.product.cpu.abilist
armeabi-v7a,armeabi                # ← 连 arm64-v8a 都没有

$ getprop ro.product.cpu.abilist64
（空）                               # ← 64 位列表直接为空

$ getprop ro.zygote
zygote32                           # ← Zygote 也是 32 位的

$ ls /system/lib64
ls: /system/lib64: No such file or directory   # ← 不存在

$ zcat /proc/config.gz | grep '^CONFIG_ARM64='
CONFIG_ARM64=y                     # ← 内核确实是 64 位

结论：内核 64 位，用户空间纯 32 位。

这台表都已经到 Android 17 了，用户空间仍然是 32 位。这不是首发疏漏，而是刻意的长期选择——1.79 GB 内存，32 位指针省内存是实打实的。

文档那句话到底什么意思

回去仔细读原文，其实它没说谎：

  • 标题「64-bit kernel and user space」是个光秃秃的名词短语，读起来像设备规格声明
  • 正文其实是个行动号召：「让您的应用为仅支持 64 位架构的硬件做好准备」
  • 关键词是 emulator（模拟器是 64 位专用）和 upcoming（面向未来硬件）

这类「平台能力」文档不能拿来判断具体设备。信 getprop，不信文档。

正确姿势

Magisk v30.7 的 APK 里 lib/armeabi-v7a/ 和 lib/arm64-v8a/ 两个都有。取 32 位的 libmagiskinit.so，在 adb shell 里 patch init_boot，只刷当前 slot，另一 slot 留原版保底：

# 在表上 patch（确保用的是 armeabi-v7a 的二进制）
adb shell /debug_ramdisk/su -c id   # 验证 root
# uid=0(root) gid=0(root) ✓

成功的那一刻真的想开香槟。

§2 圆形屏幕上点不到的 Magisk 授权弹窗

Root 成功后遇到的第一个问题：Magisk 的 su 授权弹窗在圆形屏幕上，按钮被截掉了，点不到。

ADB shell 走 uid 2000 早就授权过了，所以 adb shell su 畅通无阻。但任何其他 App 请求 root 都会弹窗——而弹窗的「允许」按钮恰好在圆屏的裁切区域。

把 magisk.db 拉出来一看：

-- settings 表：
('bootloop', 0)        -- su_auto_response 根本不在里面！

-- policies 表：
(2000, 2, 0, 1, 0)     -- 只有 shell uid 被授权

之前尝试的 REPLACE INTO settings ... su_auto_response=2 压根没落库——引号在 bash → adb shell → su -c 三层传递中被吃掉了。

解法（最外科的）：直接往 policies 表插目标 App 的 uid：

# 查 uid
adb shell dumpsys package <包名> | grep -m1 userId=

# 授权（policy=2 = ALLOW，until=0 = 永久）
adb shell /debug_ramdisk/su -c "magisk --sqlite \
  \"INSERT OR REPLACE INTO policies (uid, policy, until, logging, notification) \
    VALUES (<uid>, 2, 0, 1, 0)\""

Magisk 每次 su 请求实时查表，不用重启 daemon 就生效。

踩坑：magisk --sqlite "SELECT * FROM settings" 里的 * 会被 shell 当 glob 展开成 /data/adb/adb_keys。最稳的做法是把 magisk.db 拉出来本地读/改。

2 小时！ 逐秒心率的原始数据只在表上留 2 小时。

而且清理逻辑是搭在写入路径上的——不是定时器，而是新数据比上次清理晚 5 分钟就触发一次。与是否上传无关，离线超 2 小时的数据源头就没了。

CleanWorker 唯一的「护身符」是 requiresCharging = true——只有在充电时才跑 30 天清理。所以不充电就不清理长期数据。但 2 小时心率的清理不受这个限制。

这就意味着：如果不做任何干预，你一天 24 小时的心率数据，在表上最多只能看到最近 2 小时。

赶紧写归档系统。

§4 逐秒心率保命系统：从 v1 到 v6 的六代守护进化史

架构

表端守护（60min 轮询）
  ├─ cp 13 个 Fitbit 数据库 + ECG → /data/local/tmp/hr_archive/snap/
  ├─ mtime 去重（没变不拷）
  ├─ journal 非空跳过（防撕裂快照）
  └─ 按天数滚动保留（默认 730 天）

PC 端脚本（archive_hr.py）
  ├─ ADB 增量拉取 snap/
  ├─ SQLite 智能合并到 hr_archive.db
  └─ ECG 原始文件留存

看起来很简单对吧？然后就开始了长达三天的守护进程调试地狱。

v1-v2：天真的 sleep 3600

# 最初的想法
while true; do
    archive_once
    sleep 3600   # 每小时归档一次
done

翻车：上线首日 22 小时只跑了开机那一次。

取证发现 sleep 3600 的子进程从 10:41 一直睡到 13:44 才醒——将近 3 小时。

根因：toybox 的 sleep 走 CLOCK_MONOTONIC，不含 suspend 时间。 手表大部分时间在深度休眠，单调时钟是停的。要攒够 1 小时「清醒时间」才醒，表一天清醒净时长根本不够。

血的教训：看进程活着 ≠ 服务在跑，要看产出（log 周期）。

丢失了 09-18 12:44 ~ 09-19 11:32 的逐秒心率，含一整晚睡眠心率。永久缺失。

v3：拆小睡 + 墙钟

# v3 的改法
chunk=30   # 30 秒一小觉
next_at=$(( $(date +%s) + interval ))
while [ "$(date +%s)" -lt "$next_at" ]; do
    sleep "$chunk"
done
archive_once

效果：白天好了，2 分钟测试周期误差 <1 分钟。恢复 60 分钟正式周期。

v4：夜里 30 秒也不够

翻车：09-20 凌晨 03:03 → 08:17 守护整整 5h14m 才醒一次。

30 秒单调时钟在深度休眠时也攒不出来。临时将 chunk 降为 5 秒。

v5：5 秒也救不了深度 suspend

翻车：今晨 03:52 → 06:36 睡了 2h44m，06:36 → 09:39 睡了 3h03m。

根因：夜间系统进入 deep suspend，单调时钟彻底静止。光靠小睡只能在「醒了的时候检查有没有到点」，救不了「到点了但没醒」。

v5 探索：RTC 硬件闹钟

引入内核 RTC 闹钟：

echo "$next_at" > /sys/class/rtc/rtc0/wakealarm

到点由 PMIC 强制唤醒 AP，不管系统有多深的休眠。

但又有新问题：RTC wakealarm 唤醒 AP 后，无 wakelock 的情况下系统仅停留约 400 毫秒 就重回休眠。如果 chunk=5s，单调时钟在 400ms 内只能累积 0.4s，sleep 来不及返回，硬件闹钟已消耗失效——又卡住了。

v6：终极方案

chunk=0.3   # 300ms < 400ms 唤醒窗口

核心：chunk 必须小于 RTC 唤醒窗口（~400ms），确保在硬件闹钟唤醒的那 400ms 里 sleep 必定能返回，然后命中 now_epoch >= next_at 触发归档。

配套优化：

  • 归档前立即 cmd power set-wakelock acquire PARTIAL_WAKE_LOCK，保证拷贝期间不进 suspend
  • 归档完释放 wakelock
  • pid 校验每 10 次（~3 秒）才查一次，避免高频磁盘 IO
  • stop 命令 kill -9 守护 + toybox pkill -9 -P 清子进程 + 清 wakealarm

最终状态：精确到分钟级的 60 分钟轮询，严守 2 小时清理红线，夜间深度休眠也不破线。

其他踩过的坑

坑详情

§5 ECG 心电图解码：逆向 libecg.so 破解 BIFA 格式

格式概述

ECG 录音存在 /data/data/com.fitbit.ecg/ecg-*.dat，每个文件固定 19,858 字节。

通过对 com.fitbit.ecg APK 中的 libecg.so（ECGlib）进行静态逆向，加上双样本统计验证，破解了完整的文件格式：

[0,4)     magic "BIFA"（"AFIB" 反写——房颤检测，懂了）
[4,8)     u32 小端，数据区长度
数据区：
  0x00   12B   固定段（版本/标志）
  0x0D   f32   ~94.05 / 98.59（疑似心率）
  0xDD   u32   采样数 = 7500
  0xE1   15000B  ★ ECG 波形：7500 个 int16 小端 @ 250Hz = 30.0 秒
  帧时间戳表：469 × 8B（u32 微秒, u32 0）
  注解区：
    469B  帧有效标志
    3×f32 信号质量（有效信号/伪影/噪声）
    u16[] QRS onset 序列（每次心搏的检测触发点）
  尾 32B  校验和（keyed 算法，未破）

解码器核心

MAGIC = b'BIFA'
FS_HZ = 250.0  # Fitbit ECG 采样率

# 读取波形
n_samples = struct.unpack_from('<I', body, 0xDD)[0]  # = 7500
wave_raw = body[0xE1:0xE1 + n_samples * 2]
samples = np.frombuffer(wave_raw, dtype='<i2').astype(np.float32)
# → 7500 个采样点，30 秒 @ 250Hz 的完整 ECG 波形

R 峰定位的坑

第一版用 argmax(|s|) 定位 R 峰，结果被 ecg-001 里 29.776 秒处的 -32768（接触丢失饱和值）拉偏了——它是最大绝对值，但不是 R 波。

修复：掩蔽饱和伪影 (|s| > 30000) → 去基线 → 取正向最大偏转：

def first_rpeak(s):
    sat = np.abs(s) > 30000          # 饱和伪影
    x = s.copy()
    x[sat] = np.nan
    base = float(np.nanmedian(x))    # 去基线
    x = x - base
    x[sat] = -np.inf                 # 排除候选
    return int(np.argmax(x))         # 真正的 R 波

未破的部分

  • 校验和算法（尾部 32 字节，前 16 字节有效，keyed 算法，非 MD5/SHA1/SHA256/CRC64 裸算）
  • 注解区尾部 16B 里那个 0x00065B8F 的语义
  • 0x00 ~ 0xDC 元数据字段的完整语义
  • rsp-*.dat 是 A128GCM 加密的服务器回包，无密钥，懒的磕

§6 蓝牙断连取证：157 秒的沉默之谜

某天发现手机和手表的蓝牙连接经常断开。手机侧先做了取证，结论是「对端（手表）不应答寻呼」。于是在手表侧做了验证。

四次断连的时间线

#手表侧断连时刻失联时长失联期间 AP 状态
A18:35:5310.4s频繁唤醒（用户醒着）
B00:25:33170.7s只醒了 2 次后 157 秒死寂
C04:13:042.3s断连瞬间就醒着
D11:39:18<1s用户在操作

决胜证据：batterystats

00:25:36.138  +running  wake_reason="16 mpm"    ← 断连后 3.1s AP 醒
00:25:37.184  -running                           ← 又睡了
00:25:49.092  +running  wake_reason="pm8xxx_rtc_alarm"  ← 只醒 0.4s
00:25:49.515  -running                           ← 又睡了
      ┌──────────────────────────────────────┐
      │   157.1 秒，零个 +running            │  ← 手机 6 次寻呼全在这里
      └──────────────────────────────────────┘
00:28:26.631  +running                           ← 终于醒了
00:28:26.511  ACL Connection request             ← 145ms 内重连成功

4/4 案例完全单调：失联时长 = AP 挂起时长。

根因分析

手表的蓝牙控制器（Qualcomm WCN 系）的能力报告：

sniff_offload_support: 0           ← 链路省电不能下放给控制器
le_connectability_state: "DISARMED" ← 自主接受连接的 offload 未武装

这块控制器没有「AP 挂起期间自主接受连接」的能力。 AP 一睡，新连接就进不来——认证、加密、SDP、RFCOMM 建链全在主机侧。

一个推理陷阱

「主机侧没有 Connection request」不能证明「射频没收到寻呼」。

BR/EDR 的寻呼应答（FHS 包）在控制器层完成。控制器回了 FHS 但手机没收到的话，连接不会进入下一阶段，控制器不通知主机——主机侧照样没记录。需要 HCI 层日志才能区分。

排除清单

假设裁决
手表离腕✅ 排除——心率连续无空档（937/937/938 条）
在充电✅ 排除——18 小时纯电池
Wi-Fi 共存干扰✅ 排除——Wi-Fi 全程关闭
蓝牙固件崩溃✅ 排除——SSR dump 全空，协议栈未重启
射频完全死亡✅ 排除——断连后 2-3s LE 广播就起来了

§7 COMPANION_PROXY：一个伪装成网络的 TCP 代理

在研究「表怎么上网」的过程中发现了一个有趣的架构。

误以为

「蓝牙伴侣代理（COMPANION_PROXY）？那是手机隧道，与此无关。」

错了。它就是答案。

实测发现

关掉 WiFi 后，表上出现了这样一个「网络」：

NetworkAgentInfo{
  network{112}
  ni{COMPANION_PROXY CONNECTED}
  nc{ Transports: BLUETOOTH
      Capabilities: INTERNET & VALIDATED & NOT_METERED & NOT_VPN }
  lp{ InterfaceName: lo
      Routes: [0.0.0.0/0 -> 127.0.0.1 lo] }
}
Active default network: 112   ← 它成了默认网络

到底是什么？

不是热点，不是 BT PAN，是一个「伪装成网络的应用层透明 TCP 代理」。

三点：

  1. 一个 root 进程在监听本地端口：

    tcp 0 0 127.0.0.1:59523 0.0.0.0:* LISTEN  /sysproxy

  2. iptables 把所有 TCP 劫到那个端口：

    iptables -t nat → REDIRECT tcp 0.0.0.0/0 → redir ports 59523

  3. 接口是 loopback，路由指向自己

完整链路：

App 发 TCP → 内核路由到 lo → iptables REDIRECT 到 127.0.0.1:59523
→ sysproxy 接住 → 经蓝牙 Data Layer 隧道到手机 → 手机代连 → 原路返回

对比

WiFi 热点 / BT PANCOMPANION_PROXY
层次网络层（真 IP 接口）应用层（TCP 代理）
接口wlan0 / bt-panlo (loopback)
谁出网表自己手机代出
表有独立 IP 吗有没有

实际意义：出门带手机 + 手机开着蓝牙 → 表就全天在线，不用 WiFi、不用 eSIM、不花钱。

一个坑

之前在表上常挂 http_proxy=192.168.1.9:10808 指向家里 PC。在家没问题；出门后家里 PC 不可达 → 遵守系统代理的流量全去连 1.9 然后失败 → 反而把 COMPANION_PROXY 堵死 → 表现为「蓝牙同步不好使」。

而 COMPANION_PROXY 本身已提供完整互联网（裸 TCP 也通），表上再挂一层代理是冗余且有害的。

§8 表上工具箱：QuickTools App 与免模块 SSH

PW2 QuickTools

既然要经常调整代理、SSH、WiFi、ADB 的开关，不如直接在表上做一个 App。于是有了 QuickTools——一个给圆形 Wear OS 屏幕设计的简洁控制面板：

  • SSH 开/关：拉起/杀掉 sshd
  • WiFi 开/关：搞定 Wear OS 的 Clockwork 策略引擎压制
  • 代理编辑：只填后两段 192.168.__.__ ，省得在表上敲一长串
  • 代理开/关：一键设置/清除全局 HTTP 代理
  • ADB 开/关
  • 连通性测试：Google 204 探测

WiFi 的特殊处理

Wear OS 有个 Clockwork 策略引擎——你光跑 cmd wifi set-wifi-enabled enabled，如果蓝牙连着手机，系统会把 wlan0 压制在休眠状态。必须三件套一起来：

settings put system clockwork_wifi_setting on
settings put global wifi_always_requested 1
cmd wifi set-wifi-enabled enabled

连通性测试不能用 ping

原因：

  1. COMPANION_PROXY 是 TCP 代理，iptables 规则只匹配 TCP；ICMP 不进 sysproxy → 直接丢
  2. Android 应用没有 CAP_NET_RAW，InetAddress.isReachable() 退回 TCP echo port 7 → 假阴性
  3. ping 通只证明包到了，不证明 DNS 能解、代理能转发

正确做法：HTTP GET https://www.gstatic.com/generate_204，看是否 204。响应体 0 字节，省流量省电。

免模块独立 SSH

不要装 Magisk 模块——模块 = /data/adb/modules/<id>/ 下的脚本，每次开机 root 执行。挂了就 bootloop。

SSH 的正确做法：push 32 位 OpenSSH 二进制到 /data/local/tmp/ssh/，手动拉起：

LD_LIBRARY_PATH=/data/local/tmp/ssh/lib \
  /data/local/tmp/ssh/bin/sshd -f /data/local/tmp/ssh/etc/sshd_config -p 2222

核心坑点：Android 没有 /etc/passwd，sshd_config 必须加：

UsePrivilegeSeparation no
StrictModes no

进程托孤给 init（PPID=1），强杀 App、表息屏都不影响，常驻监听 0.0.0.0:2222。不跑时 0 耗电，零开机风险。

PC 端直连：

ssh pw2        # 直连 192.168.1.10:2222 root 免密

§10 杂项踩坑与红线清单

别碰

  • ❌ Magisk 不要点「修复运行环境 / Direct Install」
  • ❌ 不要刷 boot.img，只动 init_boot
  • ❌ 不要随便接系统 OTA（A/B 分区写入会丢 Root）
  • ❌ 不要装 Magisk 模块
  • ❌ init_boot.img 原版别删（救砖用）

OTA 拦截

系统推送季更 OTA 时，一旦插充电，update_engine 会在后台把官方镜像写入 Inactive 槽位，重启后丢 Root。

# 终止并重置
update_engine_client --cancel
update_engine_client --reset_status
setprop ctl.stop update_engine

# 清空 OTA 包
rm -rf /data/ota_package/*

# 禁用 GMS 更新组件
pm disable com.google.android.gms/.update.SystemUpdateService
pm disable com.google.android.gms/.update.SystemUpdateWearableActivity
pm disable com.google.android.gms/.update.SystemUpdatePersistentListenerService
pm disable com.google.android.gms/.update.SystemUpdateGcmTaskService

Play 商店后台唤醒压制

Play 商店在插电充电时频繁唤醒（连续持有 Wakelock 达 2 分 40 秒，发热）：

pm disable com.android.vending/com.google.android.finsky.scheduler.process.mainimpl.PhoneskyJobServiceMain
pm disable com.android.vending/com.google.android.finsky.scheduler.process.backgroundimpl.PhoneskyJobServiceBackground

手动打开商店仍可正常更新。

「每次重启都要重新授权 ADB」的一劳永逸解法

adb push ~/.android/adbkey.pub /data/local/tmp/
adb shell su -c "cat /data/local/tmp/adbkey.pub >> /data/misc/adb/adb_keys"
adb shell su -c "chown system:shell /data/misc/adb/adb_keys"
adb shell su -c "chmod 640 /data/misc/adb/adb_keys"
adb shell su -c "restorecon /data/misc/adb/adb_keys"

之后插线即用，重启也不丢。

吸收的经验

  1. 信 getprop，不信文档。 三次 bootloop 的根子就是拿文档的结论选 magiskinit 架构。
  2. 看进程活着 ≠ 服务在跑。 要看产出。那个 sleep 僵尸进程让我丢了一整晚的心率数据。
  3. 嵌入式系统的时钟不止一种。 CLOCK_MONOTONIC 不含 suspend 时间这件事，在桌面/服务器上几乎不会遇到；但在低功耗设备上，这是生死攸关的差异。
  4. 反编译比文档靠谱。 Fitbit 的 2 小时清理窗口、CleanWorker 的 requiresCharging、ECG 的 BIFA 格式——没有一样是公开文档能查到的。
  5. COMPANION_PROXY 是个精巧的设计。 不开热点、不用 PAN，一个 loopback + iptables REDIRECT + 蓝牙隧道就实现了透明 TCP 代理。省电、无感、免费。

AI 辅助的体验

干了许多：

  • ECG 格式的逆向分析和解码器编写
  • 守护脚本的多版本迭代
  • 蓝牙取证报告的生成
  • 可视化面板的前端开发

但 AI 也犯了不少错——比如第一版 R 峰检测被饱和值骗了、grep -q running 的子串陷阱、守护进程没考虑 CLOCK_MONOTONIC 的问题。每一个都是在设备上实测才发现的。

AI 是很好的加速器，但不是最终裁判。实测永远是唯一的真理。
